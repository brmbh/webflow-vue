The moveWhy 01, 02 and 03 are one idea

Three concepts, one move: push the coupling point into the markup.

Every one of them takes something currently written in the bundle and writes it next to the thing it describes instead.

Right now three separate contracts bind our two halves together, and all three are maintained twice — once in src/, once in the Designer, by different acts, with no mechanism forcing agreement. That is the shape of the 2026-08-11 failure: the markup called helpers the bundle didn't expose, and nothing said so until the configurator rendered empty.

01+ 02Boundaries & discovery

Delete the mount manifest.

petite-vue's mount() sweeps for [v-scope], drops any nested inside another, and mounts each match as a root — all sharing one context. The list of islands is not written anywhere. It is found.

We already mount one app per island, so the sweep is the only missing piece. Same architecture, one less thing to keep in sync.

Now — a manifest that must be maintained
// src/main.js — grows with every island
mountIsland('#vf-counter', 'counter', setup)
mountIsland('#vf-status',  'status',  setup)
mountIsland('#vf-cms',     'cms',     setup)
mountIsland('#vf-cart',    'cart',    setup)

Add an island → edit, rebuild, reupload, bump bridge, republish

Concept applied — a sweep that never changes
// src/mountScopes.js — ~30 lines, written once
export function mountScopes(store) {
  const roots = [...document
    .querySelectorAll('[data-vf-scope]')]
    .filter(el => !el.parentElement
      ?.closest('[data-vf-scope]'));

  for (const el of roots) {
    const local = new Function(
      `return (${el.dataset.vfScope || '{}'})`
    )();
    createApp({ setup: () =>
      ({ ...store, ...reactive(local) })
    }).mount(el);
  }
}

Add an island → Designer only

What this costs — not hidden

Each scope is still its own Vue app, so Vue's mount still rebuilds that subtree — keep scopes small, and keep sliders and lightboxes outside them. Child scopes can't read a parent's locals the way petite-vue's prototype chain allows, so shared state still goes through the store. And new Function() runs a Designer-authored string: fine on our own sites, never over user-generated content.

03Named elementsRefs instead of selectors

The markup should name its own parts.

In petite-vue, a plain ref="cartCount" attribute registers the element in $refs. No selector, no class dependency, no coupling to a class name the designer is free to rename during a restyle.

This is the cheapest of the three and it removes a real category of breakage: right now a class rename in the Designer can silently break bundle code that queried it. Vue 3 supports ref in in-DOM templates already — we simply aren't using it, and a data-vf-ref sweep in the same pass as 01 covers the rest.

Worth pairing with concept 06: petite-vue removes each directive attribute once it has been processed, so the live DOM stays clean and a second mount is a no-op. Cheap hygiene, and it makes re-mounting after a Webflow re-render safe.

04+ 05The judgement calls

Two that depend on what WebflowVue is for.

04 · Lifecycle declared in the markup

v-on:vue:mounted="…" lets an element say "when I appear, run this." For a setup where you're constantly re-initialising GSAP and IX2 around mounted regions, a data-vf-on-mount hook means that wiring lives on the element it animates rather than in a lifecycle block that has to re-find it.

Adopt it if the animation wiring is the part that keeps breaking. Skip it if onMounted in the island's setup is already where you'd look.

05 · No-build as a first-class mode

petite-vue's default story is a CDN tag and an attribute — no Vite, no bundle, no upload. That isn't a technical concept so much as a product one, and it maps onto a real tension in WebflowVue: Brew Lab is too advanced to demo, which is why the 17-line hello.js exists.

Concepts 01 and 03 make a genuine no-bundle tier possible — Vue from CDN, one generic sweep script, all behaviour declared in attributes. Simple islands (toggles, filters, counters) ship with zero infrastructure; complex ones (configurator, cart, CMS parsing) keep the bundle. That's a two-tier concept worth deciding on deliberately rather than drifting into.

07+ 08What not to copy

Two concepts we should consciously not take.

07 · Scope inheritance

createScopedContext builds a child scope as Object.create(parentScope) wrapped in a Proxy whose set trap forwards writes of unknown keys up to the parent. Elegant — child scopes read parent state transparently, writes fall through unless the child owns the key.

Our registry is flat: every island names its store explicitly. That is more typing and it is the better trade for us. Given a failure mode where a section silently blanked, being able to see which state an island touches beats not having to type it.

08 · Per-expression failure isolation

petite-vue try/catches every individual expression, so a broken binding kills one binding and the section still renders. Vue's render function is monolithic — one bad expression blanks everything.

I want to be exact here, because I got this wrong earlier: this cannot be retrofitted. The guardTemplateApi Proxy can't match it. petite-vue catches around the whole expression, so a missing helper yields undefined; to do the same we'd need a value that is both callable and falsy, and JavaScript has exactly one of those and it is not available to us. The documented "missing value takes the wrong branch" limitation is forced, not an oversight.

So the concept-level lesson inverts

Because Vue cannot degrade gracefully, prevention is the only lever we have. npm run check:dom-contract should be a hard pre-deploy gate, not an optional script someone remembers to run. petite-vue can afford a loose markup contract; we structurally cannot, so ours has to be enforced instead.

NextThe smallest honest test
